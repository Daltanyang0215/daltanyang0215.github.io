사례 1

데미지 계산을 분리하고, 수치 회귀 검사로 지키기

약 510건 수치를 바꿀 때마다 콘솔에서 자동으로 도는 검사 · 2026년 10월 기준 전부 통과
상황

모드가 늘면서 수치 하나를 바꿀 때 다른 조합이 깨지는지 사람이 매번 확인할 수 없게 됐습니다. 데미지 계산이 Unity 안에 있으면 확인할 때마다 에디터를 켜고 플레이해야 해서, 확인 주기가 에디터에 묶였습니다.

판단 근거
  • 턴제 전투라 플레이어의 조작 실력이 결과에 거의 영향을 주지 않습니다. 계산을 화면과 떼어 놓아도 됩니다.
  • 모든 클래스가 MonoBehaviour일 필요는 없고, 순수 계산 클래스는 최적화와 가독성에도 유리합니다.
  • 분리하면 UI가 단순한 버튼이어도 기능을 점검할 수 있고, 통계도 플레이 없이 코드로 낼 수 있습니다.
선택과 이유

데미지 계산을 UnityEngine에 의존하지 않는 순수 C# 엔진으로 분리하고, 콘솔에서 바로 돌리는 회귀 검사를 만들었습니다.

게임·에디터 밸런스 도구·검사가 같은 엔진 코드를 씁니다. 검증 도구가 공식을 따로 구현하다 원본과 어긋나는 일을 막기 위해서입니다.

결과

검사는 60여 건에서 시작해 약 510건이 됐습니다. 모드가 슬롯 한도에 걸려 아무 표시 없이 장착되지 않던 문제를 플레이 전에 검사 실패로 먼저 발견했습니다. 코드를 바꾼 뒤에는 실패 건수가 아니라 실패 항목 이름을 이전 커밋과 대조해, 새로 깨진 것만 골라냅니다.

한계

회귀 검사가 지키는 것은 "바뀌지 않았음"까지입니다. 밸런스가 지금 어디에 있는지는 따로 잽니다.

  • 모드 조합의 출력 상한을 빔 서치로 재는 콘솔 도구
  • 런 단위로 몇 스테이지에서 막히는지 보는 에디터 도구
  • 아래 사례 2의 성향별 시뮬레이션

코드: unity-portfolio / DamageEngine · DamageLabEditor

사례 2

클리어가 운인지 판단인지, 시뮬레이션으로 확인하기

40.5% → 81.5% 같은 시드에서 '탐욕' 시나리오와 '보스 대비' 시나리오의 클리어율 (당시 측정)
상황

기능은 빠르게 늘었지만 밸런스는 직접 플레이로 검증하기에 역부족이었습니다. 혼자 플레이해서는 조합별·성향별 클리어율처럼 많은 판에서 나오는 정보를 알 수 없습니다.

확인하려던 것

"결과가 운인가, 판단인가." 같은 조건에서 고르는 방식만 달리했을 때 클리어율이 갈린다면, 판단이 결과를 결정하는 게임이라고 볼 수 있습니다.

선택과 이유

게임과 같은 계산 코드로 런을 반복하는 시뮬레이터를 만들었습니다. 플레이 방식을 나눈 시나리오 10종을 정하고, 시나리오마다 200회씩 돌렸습니다.

  • 탐욕: 당장 화력이 크게 오르는 모드만 고릅니다.
  • 보스 대비: 다음 보스를 보고 그 보스에 대응하는 모드를 고릅니다.
결과
탐욕40.5%
보스 대비81.5%

같은 시드에서 고르는 방식만으로 클리어율이 두 배 가까이 갈려, 판단이 클리어를 결정한다는 것을 확인했습니다.

바꾼 것
  • 탄약을 줄여 적은 탄으로 진행하는 빌드는 모드 조합을 마친 상태에서도 다른 빌드의 절반 이하 클리어율이라 폐기했습니다.
  • 전기 속성 빌드가 32%로 다른 속성 빌드(87.5%)보다 크게 낮아 피해량을 올렸습니다.
한계

당시 측정한 수치라 지금의 밸런스와는 다릅니다. 시나리오는 제가 정한 선택 규칙이라, 실제 플레이어의 선택과는 다를 수 있습니다.

작업 방식

AI에게 구현을 맡기고, 기준은 밖에 두기

Claude Code에 구현을 맡기면서, AI가 기억해 주길 기대하지 않고 설계·검수·진행 상태를 문서와 검사로 밖에 두는 방식으로 운용합니다.

  • 설계는 직접: 인터페이스·데이터 구조·런 상태 분할은 직접 정하고, 내부 구현만 맡깁니다.
  • 검수는 검사로: 맡긴 코드는 사람이 매번 읽는 대신 위의 회귀 검사가 수치로 검수합니다.
  • 맥락은 문서로: 진행 상태와 결정 사항을 작업 로그와 규칙 문서에 남겨 세션이 바뀌어도 맥락을 잇고, 로그가 커지면 지난 기록을 보관 문서로 옮겨 읽는 비용을 관리합니다.
